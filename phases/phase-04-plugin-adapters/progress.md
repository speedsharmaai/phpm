# Phase 04 progress

What was checked, and how. Numbers are from the owner's Mac (M1 Pro, macOS
26.5.1, APFS, Composer 2.10.3, PHP 8.4.13 without intl) unless a row says
otherwise.

## Adapter registry and groundwork

`phpm install --explain` decides, before anything is placed, whether a
native adapter covers every active plugin (`crates/phpm/src/adapters/`).
Installer-type plugins (composer/installers, the WordPress core installer)
go native only together, since their install paths feed every other
adapter's own path lookups (`Paths`). Hooks fire in Composer's real order:
`pre-install-cmd` (fallback only, nothing native needs it) before
placement, `pre-autoload-dump` before the autoload is generated,
`post-autoload-dump` and `post-install-cmd` after. A plugin covers its
package only at the exact normalised version (or, for a dev-branch package
with no tagged release, the exact locked git commit) whose source was read
and compared; anything else declines to Composer, as does any input shape
an adapter does not reproduce exactly (decision 0004 — byte-identical or
fall back, never partial).

## composer/installers

Every installer type at the locked version (2.3.0): framework prefix
lookup as `Installer::findFrameworkType`, each installer's `supports()`
pattern and locations, `inflectPackageVars`. Root `extra.installer-paths`
with `{$name}`/`{$vendor}`/`{$type}` and `type:`/`vendor:`/package-name
keys, `extra.installer-name`, `extra.installer-disable`. Checked against
the real plugin on 855 type and name cases
(`crates/phpm/tests/golden/installers/`). Installers with side effects or
environment lookups (CakePHP's local repository check, Oxid's vendor
metadata file, Bitrix's duplicate prompt) stay on fallback.
roots/wordpress-core-installer (1.100.0 to 4.0.0, identical sources):
`wordpress-install-dir` for `wordpress-core` packages; johnpbloch's stays
on fallback.

## symfony/runtime

`vendor/autoload_runtime.php` from the package's own template with
`extra.runtime` options, `project_dir` nesting, a custom
`autoload_template`, `runtime: false`. Verified every stable tag
v7.0.0-v8.1.0 (4 content changes to `ComposerPlugin.php` in that span, each
a comment or a `\sprintf` namespace prefix, never the generated bytes); the
common case matches drupal-recommended's and symfony-demo's real
`vendor/autoload_runtime.php` byte for byte.

## phpstan/extension-installer

`GeneratedConfig.php`: extensions, `NOT_INSTALLED`, the compacted
`phpstan/phpstan` version constraint, `ignore`; absolute install paths
compared at the same path. Verified 1.4.0-1.4.3 (byte-identical sources).
The compacted constraint is the intersection of each qualifying package's
own `phpstan/phpstan` bound, the same fold `MultiConstraint::extractBounds`
does for a conjunction (reusing `phpm_lock::constraint::Constraint::bounds`
rather than porting Composer's general interval algebra); declines when
the intersection is empty rather than guess. `relative_install_path` and
the extensions' shape checked against drupal-recommended's real captured
`GeneratedConfig.php`. Declines a dev/branch-version qualifying package
(would need `getFullPrettyVersion()`'s truncated-reference suffix) rather
than guess at it.

## dealerdirect/phpcodesniffer-composer-installer

`CodeSniffer.conf`'s `installed_paths` as the plugin computes them
(`Finder` depth rules, relative paths, sort). Verified 1.2.1 only (every
release changed `src/Plugin.php`). Checked against a real install of
drupal-recommended's exact packages (drupal/coder, sirbrillig's and
slevomat's standards): identical `installed_paths` string, byte for byte.
No existing-config merge: phpm only does fresh installs, and the file is
entirely plugin-managed, so a full recompute each run matches Composer's
real first-install behaviour; written only when phpm finds at least one
`ruleset.xml`, matching `saveInstalledPaths` only running on a change.

## drupal/core-composer-scaffold

File mappings from allowed packages (implicit `drupal/core` and
`drupal/legacy-scaffold-assets`, root `allowed-packages`, recursive). Only
the plain `replace` shape (a string, or `{path, overwrite}`) is reproduced;
`append`/`prepend`/`mode` and `overwrite: false` decline rather than guess,
as does a root package with its own `drupal-scaffold.file-mapping`. Later
packages override earlier ones for the same destination, matching
`ScaffoldFileCollection`. `locations` (`web-root`, `project-root`) and the
`[web-root]`/`[project-root]` interpolator; `[web-root]/autoload.php` and
`autoload_runtime.php` regenerated from the real plugin's templates.

`.gitignore` management: phpm shells to `git rev-parse --show-toplevel` and
`git check-ignore vendor`, and only goes native when management would stay
disabled (no committed `.gitignore` ignoring `vendor`) — the real
drupal-recommended fixture's case; declines rather than reproduce the
gitignore-writing path Composer's plugin takes otherwise.

`preAutoloadDump`: the root classmap additions (conditional
symfony/http-foundation, symfony/http-kernel, symfony/dependency-injection
and psr/container files, each only when its package is locked) and
`vendor/drupal/DrupalInstalled.php` with its xxh3 versions hash. The hash
algorithm (`twox-hash`'s `XxHash3_64`, MIT-licensed; `xxhash-rust` was
tried first but rejected by `cargo deny`'s license allowlist) was verified
byte-for-byte against PHP's own `hash('xxh3', ...)` on a real fixture
before any Rust was written. The classmap addition is threaded into
`phpm-autoload` as a new `Options.extra_root_classmap`, appended to the
root package's `classmap` exactly as Composer's `AutoloadGenerator` does
for an absolute path on the root (its `install_path` is always empty, so
the path passes through unmodified).

drupal/core-project-message (prints only, verified it writes nothing to
disk) and drupal/core-recipe-unpack (`postUpdate`/`postCreateProject`
hooks, neither of which `composer install` fires) are both `Role::NoOp`.
Both are dev-branch packages with no tagged release, pinned to the exact
git commit drupal-recommended's lock locks, since the version string alone
cannot distinguish one commit on the branch from another.
drupal/core-vendor-hardening is not in the fixture; it stays on fallback.

Scaffold destinations can land in directories placement never creates
(`[project-root]/recipes/README.txt`, `web/sites/default/...`): this
surfaced as a real failure in `e2e_app_drupal_recommended` (a plain
"No such file or directory" writing `recipes/README.txt`), fixed by making
the shared adapter `write()` helper `create_dir_all` the parent first,
matching Composer's own `Filesystem::ensureDirectoryExists` before every
write. All adapters share this helper, so the fix applies everywhere, not
just to scaffold.

## php-http/discovery

Verified against the real `src/Composer/Plugin.php` at 1.20.0 (the version
drupal-recommended locks, fetched and read directly rather than guessed
at): `postUpdate` is bound to `post-update-cmd`, which `composer install`
never runs, so only `preAutoloadDump` matters for phpm. With
`extra.discovery` empty or unset — the common case, true for
drupal-recommended's real composer.json — that listener's only effect is
removing a stale `vendor/composer/GeneratedDiscoveryStrategy.php` left
behind by an earlier run; phpm reproduces exactly that. A pinned
`extra.discovery` would generate and classmap a candidate-strategy class
from the plugin's `PROVIDE_RULES`/`INTERFACE_MAP` tables; phpm declines
rather than reproduce that generation, per decision 0004.

## Exit: Bedrock and drupal-recommended install with no Composer at all

`just e2e-apps` (`e2e_app_bedrock`, `e2e_app_drupal_recommended`): each
fixture cloned at the pinned commit in `fixtures/apps.txt`, installed once
by real Composer and once by phpm at the same path, with scripts and

## Benchmark: warm, scripts and plugins on

`BENCH_SCRIPTS=1 PHPM_BIN=... tools/bench/bench.sh <fixture> composer phpm`,
each fixture installed in its real app
(bedrock@b905a0a, drupal/recommended-project@dbcffd8), cold n=3, warm n=5,
no-op n=10, one session, same machine. Raw JSON:
`bench/results/2026-10-01-phase-04-close/`.

| Fixture | Scenario | Composer (median) | phpm (median) | Speed-up |
|---|---|---|---|---|
| bedrock | cold | 136.64 s | 14.31 s | 9.6x |
| bedrock | warm | 4.496 s | **319 ms** | **14.1x** |
| bedrock | no-op | 1.204 s | **4.7 ms** | **256x** |
| drupal-recommended | cold | 105.28 s | 84.93 s | 1.2x |
| drupal-recommended | warm | 15.119 s | **1.973 s** | **7.7x** |
| drupal-recommended | no-op | 1.260 s | **5.4 ms** | **233x** |

Both fixtures went from "whole install handed to Composer" (Phase 02) to
fully native in this phase, so this is the first warm and no-op number
either has that is not Composer's own.

drupal-recommended's cold number is only a modest win: it locks 152
packages including PHPUnit, PHPStan and OpenTelemetry's dev dependencies,
and the cold scenario clears `vendor/` and every cache before each run, so
both tools re-download the same bytes from the network every time; phpm's
edge there is placement and extraction speed only, not the transfer
itself, which is the same network path for both. Warm and no-op are where
going native pays off, because nothing is re-fetched.
